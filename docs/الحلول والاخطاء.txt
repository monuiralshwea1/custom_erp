# خطأ رقم 1: رسالة «DocType Module Control Settings غير موجود» وتعليق النظام
   بعد تنزيل التحديثات إلى سيرفر الاستضافة (عدة سايتات)

## 1) الأعراض
- بعد سحب تحديثات التطبيق custom_erp من GitHub إلى سيرفر الاستضافة
  وفتح النظام بأي مستخدم، تظهر رسالة مكررة:
     «DocType Module Control Settings غير موجود.»
- النظام يعلق: لا دخول لأي واجهة ولا فتح أي مستند ولا تنقل —
  الشاشة تبقى ثابتة (واجهة الديسكت لا تكتمل تهيئتها).

## 2) الجذور الحقيقية (تحليل تفصيلي)

### الجذر الأول: الـHooks تعمل على كل سايت حتى غير المثبَّت فيه التطبيق
- ملف custom_erp/hooks.py يُحمَّل تلقائياً لكل السايتات الموجودة في نفس
  المنصة (bench)، بما فيها السايتات التي لم يُثبَّت فيها التطبيق أو لم
  يُنفَّذ عليها migrate — أي سايتات بلا DocTypes التطبيق أصلاً.
- طبقات النظام تقرأ الإعدادات هكذا:
      frappe.get_cached_doc("Module Control Settings")
  وعند غياب الـDocType تُرفع استثناء DoesNotExistError عبر frappe.throw
  فتنسج الرسالة العربية في frappe.local.message_log.
- المشكلة الدقيقة: حتى لو أمسكنا الاستثناء بـ try/except (وهذا كان
  موجوداً في الكود فعلاً)، فالرسالة تبقى معلقة في message_log الخاص
  بالطلب وتُحقن تلقائياً في استجابة كل طلب (‎_server_messages‎) —
  لهذا تتكرر الرسالة مع كل فتح صفحة أو مستند.
- مواقع النداء التي كانت تُنتج الاستثناء:
  1) custom_app/module_control/visibility.py → build_state() → get_cached_doc
  2) custom_app/module_control/sync.py → _settings_doc() → db.exists/get_doc

### الجذر الثاني: أصول JS الجديدة تحتاج بناء قبل العمل
- التحديث أضاف ملفات في app_include_js (منها dev_gate.js و
  module_control_settings.js). إذا لم يُنفَّذ bench build بعد سحب
  التحديث فالطلب على الملف يرجع 404 → تحميل الديسكت ينقطع بسبب خطأ
  JavaScript → النظام يبدو "صورة فقط" بلا أي تفاعل أو تنقل.
- وبدون bench migrate لا تُبنى جداول وDocTypes التطبيق على السايت
  أصلاً — وهذا ما يُغذّي الجذر الأول مباشرة.

## 3) الحل الجذري في الكود (مقاوم لوضع "سايت غير مهيأ")

### أ) ملف: custom_erp/custom_app/module_control/visibility.py
أُضيفت بوابة أمان متعددة السايتات:

   def app_ready():
       - تتحقق أن "custom_erp" موجود في installed_apps لهذا السايت.
       - تتحقق أن DocType «Module Control Settings» موجود فعلاً
         (frappe.db.exists) والنتيجة تُخزَّن في Redis لمدة 600 ثانية
         حتى لا يقوم السايت باستعلام تحقق في كل طلب.
       - عند أي عطل تُرجع False بدون رفع استثناء.

وأُضيفت حالة تعطيل كاملة الشكل:

   def _disabled_state():
       - قاموس بـ28 مفتاحاً مطابقاً تماماً لأشكال مفاتيح build_state()
         الحقيقي، كلها معطلة وفراغات.
       - هذا يمنع أي KeyError في أي طبقة تستهلك الحالة:
         permissions / workspace_filter / api / sync.

وأُعيدت كتابة نقاط الدخول:
- get_state(): أول سطر — إن لم يكن app_ready() تُرجع _disabled_state()
  فوراً بدون أي لمس لإعدادات غير موجودة.
- build_state(): نفس البوابة أعلى الدالة؛ وعند فشل get_cached_doc
  تُضاف استدعاء frappe.clear_last_message() لينظَّف أي رسالة سربت في
  message_log (منع تسرب التنبيه في استجابة HTTP نفسها).
- الاستثناء العام في get_state() أيضاً ينظّف الرسالة قبل رجوع الحالة الافتراضية.

### ب) ملف: custom_erp/custom_app/module_control/sync.py
- _settings_doc(): أصبح يبدأ بشروط app_ready()؛ في السايتات غير المهيأة
  يُرجع None بصمت — لا يُنفَّذ db.exists أو get_doc أصلاً.
- run_sync() (يُستدعى عبر after_migrate لأي سايت يُرَحِّل في البنش):
  أول سطر — إن لم يكن app_ready() يُرجع {"skipped": "site-not-ready"}
  بصمت ولن يحاول إنشاء إعدادات أو مساحات في سايت لا يحتوى التطبيق.
- _ensure_settings_exists(): بعد النجاح في أول إنشاء للإعدادات تنادي
  reset_ready_cache() (دالة جديدة في visibility.py) ليبدأ السايت
  يعمل فوراً بعد التثبيت/الترحيل عند إبطال الكاش.

### ج) النتيجة
- على أي سايت غير مثبَّت: طبقة التحكم صامتة تماماً (no-op) — لا رسائل
  ولا أخطاء ولا تعليق.
- على السايتات المثبَّت: كل سلوك النظام كما هو تماماً بلا تغيير.
- الكلفة: استعلام تحقق واحد رخيص كل 10 دقائق لكل سايت (مخزن في Redis).

## 4) خطوات إصلاح سيرفر الاستضافة نفسه (حتمية مع أي تحديث مستقبلاً)

بعد سحب آخر تحديث للكود، نفّذ بالترتيب (داخل مجلد المنصة):

   cd /home/<USER>/frappe-bench2
   bench build --app custom_erp        يبني ملفات JS (يمنع "صورة فقط")
   bench --site <SITE> migrate         ينشئ DocTypes/جداول التطبيق على
                                       كل سايت مثبت فيه التطبيق
                                       (كررها لكل سايت أو --site all)
   bench clear-cache                   يمسح كاش الحالة/الجاهزية
   bench restart                       يعيد تشغيل العمليات بالتغييرات الجديدة

ملاحظات:
- إن كان التطبيق غير مثبت على بعض السايتات فاتركه — الآن الطبقة صامتة
  هناك بلا أي أثر ولا يعطل النظام.
- إن أردت تثبيت التطبيق على سايت معين:
      bench --site <SITE> install-app custom_erp
      bench --site <SITE> migrate
      bench clear-cache

## 6) خلاصة منع التكرار مستقبلاً
1. أي تحديث جديد على سيرفر استضافة متعدد السايتات يجب أن يُلحق به

   أن السايت مثبته — يحيط بها app_ready().
